ResolveAI — System Design
Oct 5, 2026 · @Pipe Gen
1. Goals and scope
ResolveAI is a multi-tenant SaaS that answers customer questions from a business's own
documents, triages support tickets, calls approved tools such as order lookup, and drafts
replies that a human approves before anything consequential happens. The design is a
modular monolith: one FastAPI codebase deployed as two processes (API and worker),
one Postgres database, and Redis. It stays simple to build in 6 weeks and can be split into
services later without rewriting the domain code.
In scope for the MVP
Business admin signs up, creates a workspace, invites agents.
Admin uploads documents (PDF, DOCX, TXT, MD) to a knowledge base.
Customers chat through an embeddable widget and get answers with source
references, or are escalated to a ticket.
Incoming messages are classified (intent, category, priority) with schema-validated
output.
The agent can call a mock order-status API and propose actions such as refunds.
Every outbound ticket reply and every sensitive action needs human approval.
Dashboard shows tickets, conversations, feedback, usage and cost.
Not in the MVP: real help-desk or e-commerce integrations, email inbox ingestion, billing,
multilingual and voice, MCP server, mobile app, hybrid retrieval with reranking. The design
leaves a seam for each.

2. Architecture overview
Two clients talk to one API; the API hands slow work to one worker through Redis; both
processes share Postgres, Redis, file storage and the LLM provider.
The API answers fast and never waits on ingestion or drafting; anything slow becomes a
job the worker picks up.

Modular monolith. One Python codebase with feature modules ( auth , workspaces ,
knowledge , conversations , tickets , approvals ), run as two processes. Splitting a
module into its own service later is a deployment change, not a rewrite.
Postgres is the single source of truth, including vectors. No separate vector database
to keep in sync, and RLS covers embeddings too.
Every model call goes through one AI layer, which owns prompts, tools, retries, cost
and guardrails.
Side effects only happen through approved action records. The model proposes; a
human approves; the worker executes once.
Routers stay thin. app/api/ handles HTTP; app/modules/<feature>/service.py
holds the logic, so the worker and API share it.

The workspace is always derived from the authenticated principal, never from a
request body or query string.
Each request opens a transaction and runs SET LOCAL app.workspace_id = '<id>' .
RLS policies on every tenant table allow only rows where workspace_id =
current_setting('app.workspace_id')::uuid .
The API connects as a non-owner role ( resolveai_app ) so RLS cannot be bypassed;
migrations run as the owner role.
A repository base class adds the workspace_id filter automatically; a test suite tries
cross-tenant reads on every endpoint and must get 404.
Principals and roles
Auth details
Access token: JWT, 15 minutes, contains sub (user id), wid (active workspace), role .
Refresh token: opaque, 30 days, stored hashed, rotated on every use; reuse of an old
token revokes the whole family.
Web app keeps the refresh token in an httpOnly, Secure, SameSite=Lax cookie; the
access token lives in memory.
Widget: the page embeds a public workspace key; the API exchanges it for a 1-hour
customer session token bound to one conversation and to the site's allowed origins.

and approved actions. Anything slow or retryable runs in the worker; the API only

6.1 Documentingestion
1. Admin uploads a file. The API checks size and type, hashes it, and rejects duplicates in
the same workspace.
2. The file goes to storage; a documents row is written with status uploaded ; job
ingest_document(document_id) is enqueued.
3. Worker sets processing , extracts text per file type, and normalises whitespace.
4. Chunker splits on headings first, then into ~500-token chunks with ~60-token overlap,
keeping the heading path in chunk metadata.
5. Chunks are embedded in batches of 64, then inserted with their vectors in one
transaction (old chunks of the same document deleted first, so re-runs are safe).
6. Status becomes ready with chunk_count , or failed with an error after 3 retries. The
dashboard polls status.
6.2 Live chat answer (widget)
1. Customer sends a message with their session token. Rate limit and workspace token
budget are checked.
2. The message is stored. A fast classification call returns intent, category, priority and
confidence as validated JSON.
3. Route by intent: a knowledge question goes to RAG; an order question goes to the
get_order_status tool; refunds, complaints, account changes or low confidence go to
escalation.
4. RAG: embed the question, fetch the top 8 chunks for this workspace by cosine
similarity, drop any under the similarity threshold, keep the best 5.
5. If nothing relevant is found, the assistant says it does not know and offers a human. It
never answers without sources.
6. Otherwise the LLM answers from the retrieved chunks only, citing them. The answer
streams back over Server-Sent Events and is saved with its citations.
7. On escalation a ticket is created from the conversation and the customer is told a
person will reply.

6.3Ticket pipeline
A ticket comes from a widget escalation or the create-ticket API. The worker classifies it,
retrieves knowledge and calls read-only tools, then writes a reply_draft . Proposed side￾effecting actions become action_requests . Nothing reaches the customer until an
agent approves.
6.4 Approved actions
Every tool has a risk level. read tools (order status, knowledge search) run immediately.
write and sensitive tools (create ticket, refund, change address) only ever create an
action_requests row with status proposed .
1. An agent sees the proposed action with its arguments and the AI's reason, then
approves or rejects. Sensitive actions require the admin role.
2. Approval sets approved and enqueues execute_action(action_id) .
3. The worker re-checks status and role, then calls the tool with the stored
idempotency_key , so a retry can never refund twice.
4. The result is saved as succeeded or failed ; the audit log records who approved what
and what happened.
The model never executes a side effect itself. It can only propose one.

7. AIlayer
All model access goes through app/ai/ , so features never call a provider SDK directly.
That one seam gives retries, timeouts, cost tracking, prompt versioning and provider
swaps in a single place.
Components
LLMClient interface with complete() , complete_structured(schema) , stream()
and embed() . One provider implementation plus a FakeLLMClient for tests. Every call
writes an llm_calls row.
Prompt registry: prompts live as versioned files in app/ai/prompts/ (for example
classify_v1.md , answer_v1.md ). The version is stored on every call, so a quality
change can be traced to a prompt change.
Structured outputs: classification and drafting return JSON validated by Pydantic
models. Invalid output gets one repair retry, then falls back to needs_human .
Tool registry: each tool declares a name, description, Pydantic input schema, risk level
and handler. Only registered tools exist; the model receives their JSON schemas and
nothing else.
Agent loop: plain Python, at most 4 tool calls and 30 seconds per run. Read tools run
inline; write and sensitive tools return "proposed" to the model and create an action
request.
Retriever: pgvector cosine search scoped by RLS, similarity threshold, top-k from
settings. Keyword search on tsv and reciprocal-rank fusion are added later behind
the same function.

Guardrails against prompt injection and bad output
Customer messages and retrieved chunks are placed inside clearly delimited data
blocks; the system prompt says they are information, never instructions.
Tool arguments are validated by schema, then by business rules (the order must
belong to this workspace and this customer). The model never supplies
workspace_id , URLs or SQL.
Answers must cite at least one retrieved chunk; an answer with no valid citation is
replaced by "I'm not sure, let me get a person."
System prompts, other tenants' data and secrets never enter the context window.
Output is checked for leaked emails or keys before it is shown.

9.Background jobs and reliability
The worker is the same codebase started with arq app.workers.main.WorkerSettings .
Jobs are enqueued only after the database transaction commits, so a job never runs
against a row that does not exist yet.
Rules every job follows
The payload carries only ids and workspace_id ; the job reloads state from the
database and sets the RLS context before touching data.
Jobs are idempotent: they check current status first and do nothing if the work is
already done.
Every external call (LLM, embeddings, tools) has a timeout; LLM calls retry on 429/5xx
with jittered backoff, at most 3 times.
After the last retry the record moves to a failed state with the error, and the
dashboard shows it with a retry button.
A Redis lock per ticket stops two drafts being generated at once.
The worker logs and traces with the same request id as the API call that enqueued the
job.

10.Web app and widget
The Next.js app in apps/web serves both the agent dashboard and the customer widget.
It talks to the API only through a typed client generated from the API's OpenAPI schema,
so frontend and backend types never drift.
The widget runs in an iframe so the host site's CSS and scripts cannot reach it. widget.js
is a few lines that inject the iframe; answers stream token by token over SSE; each answer
shows its sources and thumbs up/down. The planned React Native agent app reuses the
same API and generated client.

11. Observability and evaluation
Every request gets a request_id that flows through logs, traces, jobs and llm_calls , so
one id answers "what happened to this customer message?" end to end.
Observability
Logs: structlog JSON to stdout (Cloud Logging picks them up), with request_id ,
workspace_id , user_id ; no message bodies at info level.
Traces: OpenTelemetry spans around HTTP requests, DB queries, jobs, retrieval and
each LLM call.
Metrics: request latency and error rate, job duration and failure count, LLM latency,
tokens and cost per workspace, retrieval hit rate.
Errors: Sentry forAPI, worker and web.
Alerts: API 5xx above 2% for 5 minutes, job failure spike, a workspace hitting its daily
token budget.
Evaluation (lives in evals/ , runs in CI on any change to app/ai/ )
Eval results are saved per run with model and prompt version, so a regression points at
the change that caused it. Thumbs-down feedback from production gets reviewed and
added to the datasets.

12. Deployment and environments
Three environments share one set of Docker images: local (Docker Compose), staging and
production (both on Google Cloud). Configuration differs only by environment variables
and secrets.
CI/CD (GitHub Actions)
1. On every pull request: ruff, mypy, pytest (with a Postgres service container), web lint
and type-check, and evals when app/ai/ changed.
2. On merge to main : build and push images tagged with the commit SHA, run Alembic
migrations as a Cloud Run job, deployAPI, worker and web to staging, run smoke tests.
3. Production deploy is a manual approval in GitHub on the same images, never a rebuild.
4. Rollback = redeploy the previous image tag. Migrations are written to be backward
compatible for one release (add, backfill, then remove later).
